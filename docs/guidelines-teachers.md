# Инструкция по использованию курса для преподавателя

[← К описанию курса](index.md) · [РПД](rpd.md) · [Карта курса](https://github.com/Gorod89/ITMO_study_CV_46/blob/main/course.yml) · [Инструкция студенту](guidelines-students.md)

Документ описывает полный рабочий цикл преподавателя: подготовку потока, запуск материалов, выдачу работ, проверку, защиту и обновление курса. Специфические критерии каждого КИМ находятся в каталогах `blockN_*/methodical-guidelines/teachers-assessment/`.

!!! info "Текущий статус"
    `v1.0.0` — стабильный релиз репозитория. Зафиксированы окружение, CI, CPU-smoke, документация и рубрики. Maturity курса остаётся `technical-validation`: выбранные GPU-ноутбуки преподаватель проверяет на оборудовании своего потока, а результаты апробации учитывает в следующих версиях.

## Быстрый запуск

Требуются Git, Python 3.11 или 3.12 и [uv](https://docs.astral.sh/uv/). Проверку выполняйте из чистого клона:

```bash
git clone https://github.com/Gorod89/ITMO_study_CV_46.git
cd ITMO_study_CV_46
git checkout v1.0.0
make setup
make check
make smoke
```

Для просмотра и выполнения ноутбуков:

```bash
make install-notebooks
uv run jupyter lab
```

Для CPU-профиля глубокого обучения:

```bash
make install-dl
uv run jupyter lab
```

Установка не загружает полные датасеты и крупные веса. Источники, лицензии, версии и контрольные суммы данных проверяются отдельно по [реестру данных](https://github.com/Gorod89/ITMO_study_CV_46/tree/main/datasets).

!!! important "Что фактически проверяет smoke"
    `make smoke` выполняет реальный открытый CPU-конвейер и два автономных технических ноутбука блоков 3–4 с `metadata.course_ci.smoke=true`. Они не содержат решений учебных `TODO`. Учебные ноутбуки выбранного потока всё равно запускаются отдельно.

Явное headless-исполнение выбранного ноутбука после установки нужного профиля:

```bash
uv run python scripts/smoke_notebooks.py \
  "путь/к/ноутбуку.ipynb" \
  --timeout 900
```

Скрипт не сохраняет исполненную копию. Для ноутбуков блока 3 дополнительно задайте предусмотренные ими `CV_SMOKE`, `CV_PUBLIC_CHECKS` и `CV_RUN_TRAINING`.

Все отмеченные технические ноутбуки можно выполнить отдельно:

```bash
make smoke-notebooks
```

### Что проверяет CI

- быстрый CI использует Python 3.11 и 3.12;
- запускаются Ruff, unit tests, структурная проверка репозитория/ноутбуков и проверка Markdown-ссылок;
- основной job выполняет открытый CPU pipeline, а отдельный notebook job — все отмеченные технические smoke-ноутбуки;
- полный DL-профиль и GPU-ноутбуки в CI не запускаются;
- строгую сборку сайта выполняет локальная команда `make docs`;
- отдельный workflow позволяет вручную запустить явно выбранный notebook с профилем `classical`, `deep-learning` или `yolo`.

Зелёный CI подтверждает базовый технический каркас, но не является доказательством полного воспроизведения всех лабораторных.

## Подготовка курса перед семестром

### 1. Зафиксируйте версию

1. Выберите опубликованный тег или конкретный commit.
2. Запишите идентификатор версии в LMS и не обновляйте материалы посреди выполнения КИМ без объявления миграции.
3. Сохраните копию `uv.lock`, `course.yml`, рубрик и формулировок заданий для потока.
4. После фактического пилота создайте семестровый снимок вида `2026-fall` или производный тег своего потока.

### 2. Проверьте технический контур

- выполните `make check` и `make smoke` из чистого клона;
- для каждого выбранного ноутбука выполните `Restart & Run All` в заявленном профиле;
- отдельно проверьте CPU-smoke и полный режим;
- зафиксируйте время, RAM/VRAM, объём загрузок, устройство и provider;
- убедитесь, что пути относительные, а токены и персональные данные отсутствуют;
- проверьте, что public tests дают полезную обратную связь, но не раскрывают решение.

Smoke подтверждает целостность пути `данные → provider → метрики → артефакты`, но не подтверждает качество модели. Для содержательной оценки нужен полный контролируемый эксперимент.

`pandas` входит в профиль `cv`. Ultralytics YOLO вынесен в отдельный профиль `make install-yolo`, чтобы не смешивать несовместимые сборки OpenCV. Для retrieval и ONNX используйте соответственно `make install-retrieval` и `make install-inference`. Не объединяйте профили произвольно без повторной проверки lock-файла.

### 3. Сформируйте учебную конфигурацию

Для каждой работы заранее опубликуйте:

- срок, формат сдачи и способ защиты;
- обязательный и расширенный режимы;
- датасет или правила выбора собственного набора;
- вычислительный бюджет и доступный GPU;
- baseline и изменяемый фактор основной серии;
- ожидаемые файлы и артефакты;
- рубрику и порог зачёта;
- правила использования LLM и стороннего кода;
- порядок действий при недоступности внешнего ресурса.

Если полный профиль недоступен части группы, предусмотрите одинаково оцениваемый CPU-вариант, готовые embeddings или inference на опубликованных весах. Не подменяйте исследовательский результат метриками smoke-режима.

### 4. Подготовьте данные

1. Проверьте лицензию кода, весов и данных отдельно.
2. Зафиксируйте URL, версию, дату загрузки и SHA-256.
3. Опубликуйте неизменяемый split или генератор split с seed.
4. Исключите утечку сцен, людей или кадров между train, validation и test.
5. Подготовьте открытый малый fixture на случай отсутствия сети.
6. Не размещайте закрытые, персональные или лицензионно ограниченные данные в публичном репозитории.

### 5. Разделите открытые и закрытые материалы

Публичный репозиторий содержит задания, рубрики, тренировочные вопросы, public tests и малые fixtures. Эталонные решения, ключи, hidden tests, независимые варианты и экзаменационные генераторы храните в отдельном закрытом преподавательском репозитории по [политике безопасности](assessment-security.md).

Не подключайте закрытый репозиторий публичным submodule и не передавайте секреты через ноутбуки, issue, Actions artifacts или историю Git.

## Проведение учебной работы

### До занятия

1. Проверьте ссылки, доступность данных и весов.
2. Запустите smoke на той же версии, которую получили студенты.
3. Подготовьте один корректный baseline и несколько отказных случаев для обсуждения.
4. Опубликуйте learning outcomes и критерии завершения.
5. Укажите, какие части студент реализует самостоятельно и какие служебные функции можно переиспользовать.

### На занятии

1. Начните с научного вопроса и метрики, а не с демонстрации готовой модели.
2. Покажите путь от baseline к контролируемой серии.
3. Разберите различие validation и test.
4. Проверьте, что студенты сначала запускают малый профиль.
5. Обсудите типичные ошибки и границы применимости метода.

### После занятия

1. Соберите технические сбои отдельно от содержательных ошибок.
2. Исправления общего шаблона вносите централизованно через pull request.
3. Не меняйте постановку уже выданной работы без версии и списка изменений.
4. Повторяющиеся вопросы переносите в README блока, не раскрывая hidden checks.

## Проверка воспроизводимости студенческой работы

Проверяющий должен иметь возможность получить ключевую таблицу из чистого клона или архива сдачи:

1. установить зависимости из `uv.lock`;
2. получить данные по документированной инструкции;
3. запустить smoke без закрытых ресурсов;
4. выполнить `Restart & Run All`;
5. связать строки таблицы с конфигурациями и JSONL-журналом;
6. проверить commit, seed, split, версии весов, устройство и provider;
7. убедиться, что test не использовался для выбора;
8. сопоставить сохранённые артефакты с отчётом.

Если результат не воспроизводится из-за технической ошибки, верните работу на исправление до содержательного оценивания. Если полный запуск объективно требует недоступного преподавателю ресурса, оцените заранее утверждённый воспроизводимый профиль и отдельно качество доказательств полного эксперимента.

## 1. Модель оценивания

Каждая лабораторная или домашняя работа оценивается по единой 10-балльной аналитической рубрике:

| Критерий | Баллы | Что оценивается |
|---|---:|---|
| К1. Реализация и корректность | 0–3 | Код исполняется и решает задачу; корректно используются модели, данные, библиотеки и метрики; нет утечки test |
| К2. Эксперимент и воспроизводимость | 0–3 | Есть baseline и контролируемая серия; зафиксированы seed, split, версии и конфигурации; результаты журналируются |
| К3. Анализ результатов и выводы | 0–2 | Есть сводные таблицы, визуализации и анализ ошибок; наблюдения отделены от интерпретаций; ограничения указаны |
| К4. Оформление и защита | 0–2 | Отчёт читаем, источники указаны, студент понимает код и уверенно отвечает на вопросы |

Детализация баллов:

- максимальный балл — критерий выполнен полностью;
- промежуточный балл — есть существенные, но не искажающие результат замечания;
- 1 балл — критерий выполнен фрагментарно;
- 0 баллов — критерий отсутствует или ошибка искажает результат.

| Итог | Уровень |
|---:|---|
| 8–10 | отлично |
| 6–7 | хорошо |
| 4–5 | удовлетворительно |
| 0–3 | работа не зачтена |

Порог зачёта работы — 4 балла. Правила агрегации в семестровую оценку задаются балльно-рейтинговой системой реализующего вуза. Экзамен и курсовой проект имеют собственные открытые рубрики.

## 2. Процедура проверки и защиты

1. **Технический допуск.** Проверьте комплект сдачи, public tests, запуск сверху вниз и отсутствие секретов.
2. **Методическая проверка.** Проверьте split, baseline, сопоставимость условий, выбор по validation и однократную итоговую оценку на test.
3. **Проверка доказательств.** Сопоставьте конфигурации, журнал, таблицы, графики и сохранённые предсказания.
4. **Защита.** Дайте 5–7 минут на доклад и задайте 2–4 вопроса: объяснить код, интерпретировать изменение метрики, изменить фактор или предсказать отказ.
5. **Оценивание.** Поставьте балл по каждому критерию, указав наблюдаемое основание снижения.
6. **Обратная связь.** Передайте её в течение недели и отделите обязательные исправления от рекомендаций.

Если public checks предусмотрены конкретной работой, public и hidden checks должны проверять один опубликованный контракт. Hidden check не должен требовать неописанное поведение или служить единственным основанием оценки.

## 3. Апелляция

Студент вправе запросить пересмотр, указав критерий рубрики и аргументы. Пересмотр проводится преподавателем совместно с ведущим лектором. Результатом может быть изменение оценки или её подтверждение с письменным обоснованием. Материалы и окружение первоначальной сдачи должны сохраняться до завершения апелляции.

## 4. Академическая честность и LLM

- Совпадение решений является сигналом к проверке, но не автоматическим доказательством нарушения.
- Запросите объяснение и изменение выбранного фрагмента, изучите историю Git и предоставьте право на объяснение.
- Использование LLM разрешено при раскрытии в `AI_USAGE.md`, проверке результата и способности объяснить каждый сдаваемый фрагмент.
- Автоматический детектор текста или кода не принимает итоговое решение.
- Не снижайте оценку за сам факт разрешённого использования инструмента; оценивайте понимание, корректность, атрибуцию и верификацию.

## 5. Вариативность заданий

- Назначайте индивидуальный класс, подмножество данных, backbone или один фактор серии.
- Разрешайте замену датасета только после согласования источника, лицензии, масштаба и протокола split.
- Между потоками ротируйте закрытые вопросы и данные, сохраняя одинаковые learning outcomes и рубрику.
- При переносе курса в другой вуз допускается смена прикладного домена при сохранении научного вопроса, baseline, метрик и требований воспроизводимости.

## Обновление курса

Перед изменением публичной версии:

```bash
make check
make smoke
```

Для изменённого ноутбука дополнительно выполните `Restart & Run All` в каждом заявленном профиле. Новая лабораторная принимается только при наличии:

- измеримых результатов обучения и пререквизитов;
- CPU-smoke и оценки полного вычислительного бюджета;
- фиксированного split, baseline и public tests;
- ожидаемых артефактов, рубрики и advanced track;
- data/model card и лицензионной проверки;
- ссылки на первичный источник;
- независимого воспроизведения ключевого результата.

Современные работы переводите между статусами `Watchlist → Candidate → Stable` по [политике актуализации](frontier-core-a.md). Публикация на A/A* сама по себе не делает метод обязательной лабораторной.

## Диагностика

| Симптом | Что проверить |
|---|---|
| `uv sync --locked` требует изменить lock | версия uv, Python и локальные изменения `pyproject.toml` |
| Ноутбук зависит от порядка ручного запуска | скрытое состояние; очистить kernel и выполнить сверху вниз |
| Результаты расходятся | seed, split, версии данных/весов, provider, потоки, precision |
| Полный режим недоступен | использовать утверждённый smoke/embeddings/inference-профиль, не делать вывод о качестве |
| Нужно проверить только технические smoke-ноутбуки | выполнить `make smoke-notebooks` |
| YOLO не импортирует `ultralytics` | использовать отдельный `make install-yolo`, затем перезапустить kernel |
| Ссылка или датасет исчезли | перевести ресурс в `candidate`, использовать зеркало только при допустимой лицензии |
| В истории найден секрет или ключ | остановить публикацию и выполнить процедуру из `assessment-security.md` |

## Чек-лист преподавателя

### Перед семестром

- [ ] Зафиксированы tag/commit и `uv.lock`.
- [ ] `make check` и `make smoke` проходят из чистого клона.
- [ ] Выбранные ноутбуки проверены через `Restart & Run All`.
- [ ] Опубликованы сроки, профили, рубрики и формат сдачи.
- [ ] Проверены лицензии, checksums и split данных.

- [ ] Работа воспроизводится в заявленном режиме.
- [ ] Test не использовался для выбора.
- [ ] Baseline и серия сопоставимы.
- [ ] Таблицы связаны с конфигурациями и артефактами.
- [ ] Источники и использование LLM раскрыты.
- [ ] Подготовлены вопросы по конкретному коду и результатам.

### После семестра

- [ ] Собраны технические и методические проблемы.
- [ ] Обновлён `implementation-status.md`.
- [ ] Закрыты или явно перенесены release gates.
- [ ] Создан семестровый снимок после успешного пилота.
