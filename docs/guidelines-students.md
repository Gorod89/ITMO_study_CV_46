# Инструкция по использованию курса для студента

[← К описанию курса](index.md) · [Установка](setup.md) · [РПД](rpd.md) · [Карта курса](https://github.com/Gorod89/ITMO_study_CV_46/blob/main/course.yml) · [Критерии преподавателя](guidelines-teachers.md)

Документ описывает путь от первого клонирования репозитория до сдачи и защиты работы. У каждой лабораторной есть дополнительные требования в `blockN_*/methodical-guidelines/students/`.

!!! note "Главный принцип"
    В курсе оценивается не запуск готовой модели, а воспроизводимый эксперимент:
    `данные → baseline → контролируемая серия → метрики → анализ ошибок → ограниченный вывод`.

## Быстрый старт

Нужны Git, Python 3.11 или 3.12 и [uv](https://docs.astral.sh/uv/):

```bash
git clone https://github.com/Gorod89/ITMO_study_CV_46.git
cd ITMO_study_CV_46
make setup
make test
make smoke
```

Для работы с ноутбуками:

```bash
make install-notebooks
uv run jupyter lab
```

Для CPU-профиля глубокого обучения:

```bash
make install-dl
uv run jupyter lab
```

`make setup` не скачивает крупные датасеты и веса. Не добавляйте случайные `pip install` в ноутбук и не изменяйте `uv.lock` без отдельного согласования.

!!! important "Ограничение текущего smoke"
    `make smoke` проверяет открытый CPU-конвейер и два автономных технических smoke-ноутбука блоков 3–4. Они проверяют инфраструктурный контракт, но не выполняют вашу лабораторную и не содержат решений её `TODO`. Свою работу нужно запустить явно и проверить через `Restart & Run All`.

Headless-проверка выбранного ноутбука после установки его профиля:

```bash
uv run python scripts/smoke_notebooks.py \
  "путь/к/ноутбуку.ipynb" \
  --timeout 900
```

Для работ блока 3 перед командой задайте переменные, указанные в ноутбуке, например `CV_SMOKE=1`. Скрипт выполняет ноутбук в памяти и не сохраняет новую копию.

## Как найти нужную работу

1. Посмотрите текущий блок и неделю в [`course.yml`](https://github.com/Gorod89/ITMO_study_CV_46/blob/main/course.yml).
2. Откройте README студента:
   - [блок 1 — основы CV](https://github.com/Gorod89/ITMO_study_CV_46/tree/main/block1_intro_to_VC/methodical-guidelines/students);
   - [блок 2 — технологии CV](https://github.com/Gorod89/ITMO_study_CV_46/tree/main/block2_CV_technologies/methodical-guidelines/students);
   - [блок 3 — глубокое обучение](https://github.com/Gorod89/ITMO_study_CV_46/tree/main/block3_DL_in_CV_base/methodical-guidelines/students);
   - [блок 4 — современное CV](https://github.com/Gorod89/ITMO_study_CV_46/tree/main/block4_up_to_date_CV/methodical-guidelines/students).
3. Прочитайте формулировку, learning outcomes, бюджет и ожидаемые артефакты.
4. До начала посмотрите открытую рубрику в соседнем каталоге `teachers-assessment/`.
5. Уточните у преподавателя вариант, датасет, срок и способ сдачи.

`v1.0.0` фиксирует стабильную версию файлов и открытого CPU-контура, но не означает, что любой GPU-профиль одинаково проверен на каждом оборудовании. Блоки 3–4 сохраняют статус `technical-validation`: используйте профиль, подтверждённый преподавателем, и не выдавайте smoke-метрики за полноценную оценку качества.

`pandas` входит в основной профиль `cv`. Для YOLO используйте отдельную команду `make install-yolo`; для retrieval — `make install-retrieval`, для ONNX — `make install-inference`. Профили закреплены в `uv.lock`. Не добавляйте в ноутбук собственный `pip install`.

## Рабочий маршрут одной лабораторной

### Шаг 1. Создайте рабочую копию

Не изменяйте исходную заготовку курса. Скопируйте ноутбук в выданный преподавателем репозиторий, ветку или каталог сдачи. Сохраните понятное имя работы, ФИО, группу и номер варианта.

Перед началом зафиксируйте:

- commit курса;
- версию данных и весов;
- устройство и provider;
- seed;
- идентификатор split;
- вычислительный бюджет.

### Шаг 2. Проверьте малый режим

Сначала выполните smoke и, если они предусмотрены работой, public checks. Для ЛР блока 3 точные переменные указаны внутри ноутбука; типовой порядок:

1. `CV_SMOKE=1` — малые данные и короткий запуск;
2. `CV_PUBLIC_CHECKS=1` — открытые проверки контрактов;
3. `CV_RUN_TRAINING=1` — явное включение обучения после заполнения `TODO`.

Переменные задаются до запуска Jupyter или в соответствии с инструкцией ноутбука. Smoke должен завершить весь pipeline и создать ожидаемые артефакты. Низкая или высокая метрика smoke не является содержательным результатом.

### Шаг 3. Зафиксируйте вопрос и baseline

До основной серии запишите:

- исследовательский вопрос;
- проверяемую гипотезу;
- baseline;
- единственный изменяемый фактор;
- основную метрику и дополнительные метрики;
- правило выбора checkpoint или порога;
- ожидаемое направление результата.

Не меняйте baseline после просмотра итогового test. Если в baseline найдена ошибка, пересчитайте все зависимые сравнения.

### Шаг 4. Подготовьте данные

1. Укажите источник и лицензию.
2. Используйте опубликованный split или сохраните `split_manifest.json`.
3. Не допускайте пересечения сцен, людей или кадров между частями выборки.
4. Validation используйте для выбора, test — один раз после фиксации решения.
5. Не добавляйте данные, веса и персональные изображения в Git, если это не разрешено явно.
6. Для собственного набора заполните карточку по шаблону [`DATA_CARD.md`](https://github.com/Gorod89/ITMO_study_CV_46/blob/main/templates/DATA_CARD.md).

### Шаг 5. Проведите контролируемую серию

- меняйте один фактор;
- используйте одинаковые данные, evaluator и бюджет;
- фиксируйте каждый запуск в JSONL или эквивалентном журнале;
- для стохастического обучения используйте несколько seed либо честно обозначьте `smoke-only`;
- сохраняйте не только лучшие метрики, но и время, память, неудачные случаи и ошибки.

Минимальная запись запуска:

```json
{
  "experiment_id": "lab-resnet-linear-seed42",
  "git_commit": "abcdef0",
  "data_id": "cifar10",
  "split_id": "official",
  "model_id": "resnet18",
  "seed": 42,
  "device": "cpu",
  "provider": "pytorch",
  "config": "configs/smoke.yaml",
  "metrics": {"macro_f1": 0.0},
  "artifacts": ["outputs/confusion_matrix.png"]
}
```

### Шаг 6. Выполните полный эксперимент

Переходите к полному режиму только после успешного smoke. Проверьте:

- доступный GPU и VRAM;
- ожидаемое время;
- версии CUDA, PyTorch и provider;
- объём загрузки данных/весов;
- путь сохранения checkpoints;
- возможность продолжить прерванный запуск.

Конфигурации полного режима должны быть сохранены. Не удаляйте неудачные запуски из журнала; пометьте их статус и причину.

### Шаг 7. Подготовьте отчёт

Отчёт должен отвечать на вопрос, а не повторять код. Включите:

1. постановку и гипотезу;
2. данные, split и ограничения;
3. baseline и конфигурации серии;
4. сводную таблицу метрик и ресурсов;
5. визуализации и характерные ошибки;
6. наблюдения, возможные объяснения и ограниченный вывод;
7. ссылки на источники;
8. сведения об использовании LLM;
9. команду, воспроизводящую ключевой результат.

### Шаг 8. Проверьте сдачу

Перед отправкой:

```bash
make test
make validate
```

Если вы меняли Python-модули, документацию или структуру репозитория, выполните:

```bash
make check
```

Очистите временные файлы, крупные outputs, checkpoints, токены, персональные данные и абсолютные пути. Затем выполните `Restart & Run All` в заявленном профиле.

## 1. Форма выполнения и сдачи работ

1. Работа выполняется в Jupyter-ноутбуке или, по согласованию, в виде Python-модулей с Markdown-отчётом.
2. Ноутбук должен исполняться сверху вниз без ошибок после перезапуска ядра. Невоспроизводимая работа возвращается на доработку до оценивания содержания.
3. В начале укажите ФИО, группу, номер работы, вариант, данные и источники.
4. Зависимости берите из `pyproject.toml` и `uv.lock`. Нефиксированные установки внутри сдаваемого ноутбука не допускаются.
5. Зафиксируйте seed, split, версии данных/весов, commit, устройство и provider.
6. Сдавайте работу способом и в срок, объявленные преподавателем.
7. Подготовьте доклад на 5–7 минут и будьте готовы объяснить или изменить любой сдаваемый фрагмент.

### Минимальный комплект сдачи

- исполненный ноутбук без обязательных незаполненных `TODO`;
- используемые конфигурации;
- manifest split или ссылка на опубликованное разбиение;
- журнал экспериментов;
- таблицы, графики и примеры предсказаний;
- data/model card, если применимо;
- `AI_USAGE.md`, если использовались LLM-инструменты;
- README с командой запуска и вычислительным бюджетом;
- исходный код без секретов, данных и тяжёлых checkpoints.

Каталоги `data/`, `outputs/` и checkpoints исключены из Git. Малые таблицы, конфигурации и иллюстрации передавайте способом, объявленным преподавателем; тяжёлые веса и датасеты — через LMS, объектное хранилище или ссылку с правами доступа. Не используйте Git LFS по собственной инициативе.

Формат архива, репозитория или LMS определяет преподаватель. Если требования расходятся, приоритет имеет опубликованная для потока инструкция, но научный протокол курса сохраняется.

## 2. Методика эксперимента

```text
данные → baseline → контролируемая серия → метрики и артефакты
       → анализ ошибок → ограниченный вывод
```

- **Эксперимент** — воспроизводимая конфигурация, а не отдельный запуск.
- **Baseline** — минимально разумный фиксированный вариант для сравнения.
- **Validation** используется для выбора; **test** — для однократной итоговой оценки.
- **Контролируемая серия** меняет один фактор.
- **Наблюдение** — измеренный факт; **интерпретация** — возможная причина; **вывод** — ответ в пределах проверенных условий.
- Результат без версии данных, конфигурации и связи с артефактами не считается воспроизводимым доказательством.

Подробный контракт приведён в [протоколе воспроизводимости](reproducibility.md).

## 3. Требования к отчётной части

Каждая работа завершается разделом результатов:

1. сводная таблица `конфигурация → метрики → время/ресурсы`;
2. визуализации, необходимые для ответа на вопрос;
3. анализ ошибок и неудачных случаев;
4. выводы с явными ограничениями;
5. ответы на контрольные вопросы, если они предусмотрены;
6. точная команда или последовательность запуска.

Избегайте скриншотов таблиц, если результат можно сохранить как CSV/JSON. Не вставляйте десятки однотипных изображений вместо анализа.

## 4. Справочник основных метрик

| Задача | Метрики |
|---|---|
| Классификация | accuracy, macro F1, per-class recall, confusion matrix |
| Детекция | mAP по порогам IoU, precision, recall |
| Сегментация | IoU, Dice, boundary F-score |
| Поиск | Recall@K, Precision@K, mAP, MRR |
| Производительность | mean/median/p95 latency, throughput, peak memory, model size |

Всегда указывайте протокол расчёта: split, averaging, IoU threshold, query/gallery, batch size, warmup, provider и число повторов. Одинаковое название метрики не гарантирует одинаковую методику.

## 5. Использование сторонних материалов и LLM

- Открытые данные, модели и фрагменты документации можно использовать с указанием источника и соблюдением лицензии.
- Вы должны понимать и уметь объяснить каждый сдаваемый фрагмент кода.
- Использование LLM раскрывается в файле по шаблону [`AI_USAGE.md`](https://github.com/Gorod89/ITMO_study_CV_46/blob/main/templates/AI_USAGE.md).
- Проверяйте предложенный код тестами и первичными источниками.
- Не отправляйте персональные, закрытые или лицензионно ограниченные данные во внешний сервис.
- Не указывайте LLM как источник научного утверждения; ссылайтесь на статью, документацию или данные.
- Прямое заимствование чужого решения без атрибуции и собственного понимания является нарушением.

Разрешённое использование LLM само по себе не снижает оценку. Оцениваются корректность, понимание, прозрачность и способ проверки.

## 7. Промежуточная аттестация

Первый семестр завершается [экзаменом](exam-s1.md), второй — [курсовым проектом и зачётом](coursework-s2.md). Открытые критерии и тренировочные вопросы доступны заранее. Ключи и независимые варианты публично не размещаются.

Для курсового проекта с начала работы ведите:

- постановку и сценарий эксплуатации;
- data/model card и risk register;
- журнал экспериментов;
- измерения качества и инференса;
- `AI_USAGE.md`;

## 8. Критерии оценивания

Обычная работа оценивается по 10-балльной рубрике:

| Критерий | Баллы |
|---|---:|
| Реализация и корректность | 0–3 |
| Эксперимент и воспроизводимость | 0–3 |
| Анализ и выводы | 0–2 |
| Оформление и защита | 0–2 |

Порог зачёта — 4 балла. Вы имеете право увидеть рубрику до выполнения и получить обратную связь по каждому критерию. Подробная интерпретация находится в [инструкции преподавателя](guidelines-teachers.md).

## Диагностика

| Проблема | Что делать |
|---|---|
| `uv` не найден | установите uv по официальной инструкции и перезапустите терминал |
| Неподдерживаемый Python | используйте Python 3.11 или 3.12 |
| `uv sync --locked` хочет изменить lock | не подтверждайте изменение; проверьте версию Python/uv и локальные правки |
| Jupyter не видит зависимости | выполните `make install-notebooks` или `make install-dl`, затем перезапустите kernel |
| Ноутбук работает только после ручного порядка ячеек | очистите состояние и устраните скрытую зависимость |
| Результат не совпадает | сравните seed, split, данные, веса, provider, precision и потоки |
| `make smoke` не запускает вашу лабораторную | это ожидаемо: он запускает только технические smoke; передайте путь `scripts/smoke_notebooks.py` явно |
| Не импортируется `ultralytics` | выполните `make install-yolo` и перезапустите kernel |
| Не хватает GPU | остановите полный запуск и согласуйте CPU-smoke, embeddings или inference-профиль |
| Данные/веса недоступны | не используйте случайную замену; сообщите преподавателю и примените утверждённый fixture |
| Появился `CUDA out of memory` | уменьшите batch/разрешение только как отдельную зафиксированную конфигурацию |
| Случайно добавлен токен или личные данные | не делайте push; удалите секрет из истории и немедленно сообщите преподавателю |

Если проблема общая для нескольких студентов, приложите к сообщению: commit курса, ОС, Python, команду запуска, полный текст ошибки и минимальные шаги воспроизведения. Не отправляйте токены и приватные данные.
